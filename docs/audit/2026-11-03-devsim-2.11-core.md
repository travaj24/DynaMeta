# DEVSIM 2.11.2 core groundwork (D0, v0.14.0 DEVSIM phase, 2026-11-03)

Workstream D0 of the v0.14.0 DEVSIM phase, branch `wip/dv_core`. Scope: the devsim floor, a
deterministic BLAS for DEVSIM, the `reset_devsim` workaround, what pip `mkl` does to DEVSIM's
solver, the slow semiconductor-region setup, and a rerun of every devsim-using test and validation
on 2.11.2. All numbers are MEASURED on the dev box (Windows 11, Ryzen 32 threads, 128 GB, Python
3.14, numpy 2.4.4, scipy 1.17.1) unless marked otherwise. Box A was shared by five agents during
these measurements, so wall times carry load noise.

## 2. BLAS pinning

### How DEVSIM 2.11.2 finds its math library (installed package + CHANGES, read first)

* `devsim/__init__.py` (2.11.2): on Windows, when `DEVSIM_MATH_LIBS` is NOT set, it appends
  `<sys.prefix>\Library\bin` (where pip `mkl` installs `mkl_rt.N.dll`) to `PATH` for the duration of
  the extension import, then restores `PATH`.
* The extension (`devsim_py3.pyd` strings + CHANGES 2.3.6 / 2.1.0) searches: the libraries in
  `DEVSIM_MATH_LIBS` (`;`-separated on Windows, `:` elsewhere); else the Intel MKL (`mkl_rt.N`,
  several ABI numbers; "Intel MKL with PARDISO LOADED" -> `direct_solver = mkl_pardiso`); else the
  bare names `libopenblas.dll;liblapack.dll;libblas.dll` (`.so` on Linux), loaded in order until
  every BLAS/LAPACK symbol resolves. Without MKL the `direct_solver` stays `unknown`, and
  `__init__.py` then loads `devsim/umfpack/umfshim.py`, which registers UMFPACK 5.1 as a `custom`
  solver; `umfpack_loader.py` hands UMFPACK the same `info['math_libraries']` with the same
  prefix/suffix. So the BLAS devsim picks is also the BLAS of every UMFPACK factorisation.
* `DEVSIM_BLAS_PREFIX` / `DEVSIM_BLAS_SUFFIX` (default `''` / `'_'`) are honoured only with
  `DEVSIM_MATH_LIBS`. `testing/other_blas.py` is DEVSIM's own example of pointing it at
  `scipy_openblas32` with prefix `scipy_`, suffix `_`.
* A bare DLL name on Windows is a `LoadLibrary` search: the application directory, system dirs, then
  `PATH` in order. On Linux it is `dlopen`: `RPATH` (`$ORIGIN:$ORIGIN/../lib:...`), `LD_LIBRARY_PATH`,
  the ld.so cache.

### The pin (`dynameta/carriers/devsim_env.py`)

One import home. `configure_math_libs()` runs before the first `import devsim`; `import_devsim()`
calls it and imports. All 12 package import sites (7 module-level, devsim_layered and devsim_3d
behind their friendly-ImportError `try`, impact_ionization's function-level import, eq_registry's
lazy shim, which physics_equilibrium shares) and the 23 validation scripts that imported devsim go
through it; `tests/conftest.py` calls `configure_math_libs()` before any test module's
`importorskip("devsim")`. An AST census (`test_no_devsim_import_outside_the_home`) keeps it that way.

Decision order, first match wins:

1. `DEVSIM_MATH_LIBS` set by the user: untouched (`source='user'`), prefix/suffix untouched.
2. devsim already imported: nothing can change (`'already-imported'`).
3. `DYNAMETA_DEVSIM_BLAS=off`: devsim's own search (`'off'`).
4. Not Windows and `DYNAMETA_DEVSIM_BLAS` unset/`auto`: devsim's own search (`'posix-default'`).
   `DYNAMETA_DEVSIM_BLAS=pin` applies steps 5-6 on Linux/macOS too.
5. pip `mkl` installed in this environment: `DEVSIM_MATH_LIBS=<full path of its mkl_rt>`, located
   through the `mkl` distribution's RECORD (`'mkl'`). That is the library devsim already picks when
   mkl is installed (section 4); the pin keeps it, removes the PATH lookup, and sets
   `DEVSIM_NEW_SYMBOLIC=1` unless the user set it (section 4: without it a validation fails).
6. The LP64 OpenBLAS in the installed scipy wheel, located through scipy's RECORD (never `PATH`),
   exactly one match of `libscipy_openblas(-<hash>)?.{dll,so,dylib}`, `scipy_dgemm_ scipy_dgetrf_
   scipy_dgetrs_ scipy_zgetrf_ scipy_zgetrs_` resolved by `ctypes`, and the installed devsim
   `>= 2.11.1` (read from metadata; an older devsim ignores the prefix and would fail with MISSING
   SYMBOLS): `DEVSIM_MATH_LIBS=<path>`, `DEVSIM_BLAS_PREFIX=scipy_`, `DEVSIM_BLAS_SUFFIX=_`
   (`'scipy-openblas'`).
7. Nothing found (conda scipy, Accelerate builds): devsim's own search (`'devsim-default'`).

The variables go into `os.environ`, so subprocesses inherit the same library (and treat it as a
user setting).

Why scipy's copy and not the alternatives (evidence above and here):

* scipy is a core dependency, so the file exists on every pip install; it is LP64 (devsim needs
  32-bit BLAS integers); it is the build numpy/scipy CI exercises (0.3.30, correct Zen/Haswell
  kernels); `import dynameta.carriers` already loads it (scipy), so devsim adds no new OpenBLAS
  instance, no new thread pool and no new commit. DEVSIM documents this exact use (2.11.1 #167).
* numpy's copy: ILP64 (`USE64BITINT`, `scipy_dgemm_64_`), wrong integer width for devsim.
* `ngsolve_openblas`: standard names and current (0.3.33), but only present with ngsolve, MAX_THREADS
  128 and 4 GB commit per instance, and a separate pool from scipy's.
* `scipy-openblas32` (pip): the same library as scipy's bundle with a public `get_lib_dir()`, but an
  extra dependency; not added (a dependency decision).
* MKL: kept when the user installed it (status quo), never made a dependency.

Linux: the default does not change which BLAS Linux users get (an explicit decision for the user,
see open questions). The resolution itself works there: under WSL Ubuntu, Python 3.12, devsim 2.11.2,
scipy 1.17.1 (whose wheel ships `scipy.libs/libscipy_openblas-6cdc3b4a.so`, checked in the
manylinux wheel), `tests/test_devsim_env.py` passes 21/21 with `DYNAMETA_DEVSIM_BLAS=pin` in the
decoy test. The CI `solvers` leg (ubuntu, apt `libopenblas-dev`) keeps loading the system
`libopenblas.so` exactly as before; the new test file is added to that leg's list.

Verification on this box: `info['math_libraries']` and `memory_maps()` show
`...\scipy.libs\libscipy_openblas-64eda39e79589aedb16f58e5547eb599.dll` and no Elmer DLL; in the
`[pardiso]` venv they show `<venv>\Library\bin\mkl_rt.3.dll` (+ `mkl_core.3.dll`,
`mkl_intel_thread.3.dll`) with `direct_solver = mkl_pardiso`.

## 3. `validation/ac_capacitance.py`'s `reset_devsim` workaround

The workaround deleted devices, meshes and the circuit one at a time because `reset_devsim()` broke
the next solve. Cause, read in the 2.10.0 wheel: `devsim/__init__.py` imports `umfshim`, which calls
`set_parameter(direct_solver='custom')` and `set_parameter(solver_callback=...)` ONCE at import;
`reset_devsim()` (the raw C command in 2.10) clears all parameters. 2.11.2 wraps `reset_devsim` in
`__init__.py` to call `umfshim.reload_umfpack()` afterwards (issue #169).

Reproduction (raw devsim, 1-D Laplace capacitor: build, solve, `reset_devsim()`, rebuild, solve):

| devsim | solver | after reset | second solve |
| --- | --- | --- | --- |
| 2.10.0 (venv) | UMFPACK | `direct_solver = unknown` | `DEVSIM FATAL: Unrecognized "direct_solver" parameter value "unknown"` |
| 2.11.2 | UMFPACK | `custom` | OK, mid-node V = 0.5000000000000002 |
| 2.11.2 + pip mkl | MKL-PARDISO | `mkl_pardiso` | OK, same value |

So it is fixed. `build_cap` now calls `ds.reset_devsim()` + `_R.clear(DEVICE)`. Gate: the
validation's `(C, G)` arrays for both geometries, two passes (so every geometry also follows a
clear), hashed from the raw float bytes: old clearing `c01afbae...ca24`, `reset_devsim()`
`c01afbae...ca24`, bit-identical. The validation passes (GATE A/B/CHAIN). The devsim contract is
pinned by `test_reset_devsim_keeps_the_direct_solver_and_the_answer` (fresh child: the solver
parameter survives the reset and a rebuilt device solves to bit-identical node values).

## 4. pip `mkl` (`dynameta[pardiso]`) and DEVSIM's direct solver

Yes, it changes DEVSIM's solver. Measured in a venv with `--system-site-packages` plus `pip install
mkl` (2026.2.0, `<venv>\Library\bin\mkl_rt.3.dll`), so the global environment the other agents use
was not touched:

| environment | `info['math_libraries']` | `direct_solver` | UMFPACK shim |
| --- | --- | --- | --- |
| no mkl (pre-D0) | `libopenblas.dll` (Elmer, via PATH) | `custom` (UMFPACK 5.1) | loaded |
| no mkl (D0) | `...scipy.libs\libscipy_openblas-<hash>.dll`, prefix `scipy_` | `custom` (UMFPACK 5.1) | loaded |
| pip mkl (pre-D0) | `mkl_rt.3.dll` (found via the `Library\bin` PATH append) | `mkl_pardiso` | not loaded |
| pip mkl (D0) | `<venv>\Library\bin\mkl_rt.3.dll` (full path) | `mkl_pardiso` | not loaded |

`mkl_version`: `Intel(R) oneAPI Math Kernel Library Version 2026.2-Product Build 20260915`. So
installing the `[pardiso]` extra for NGSolve also moves every DEVSIM solve from UMFPACK to
MKL-PARDISO, silently. CI has no mkl leg, so that configuration was never tested.

Speed and accuracy, representative drift-diffusion solve: the 2-D bipolar p-n diode of
`validation/bipolar_diode_2d.py` (3 variables, SRH, graded junction), all three biases, every
`ds.solve` timed (`scratchpad` script `solver_bench.py`; the default mesh and a 4x finer junction
mesh):

| mesh | solver | nodes | solves | DEVSIM solve time | result |
| --- | --- | --- | --- | --- | --- |
| default (2 nm at the junction) | UMFPACK + scipy OpenBLAS | 18357 | 23 | 132.4 s | converges |
| default | MKL-PARDISO, devsim default (symbolic reuse) | 18357 | - | - | `Convergence failure!` at all 3 biases |
| default | MKL-PARDISO + `DEVSIM_NEW_SYMBOLIC=1` | 18357 | 23 | 66.0 s | converges |
| 0.5 nm | UMFPACK + scipy OpenBLAS | 36279 | 23 | 214.6 s | converges |
| 0.5 nm | MKL-PARDISO, symbolic reuse | 36279 | 23 | 138.8 s | converges |
| 0.5 nm | MKL-PARDISO + `DEVSIM_NEW_SYMBOLIC=1` | 36279 | 23 | 148.8 s | converges |

Repeated later on a quieter box (default mesh, back to back): UMFPACK + Elmer OpenBLAS 93.8 / 94.1 s,
UMFPACK + scipy OpenBLAS 71.6 / 71.7 / 72.7 s, MKL-PARDISO + `DEVSIM_NEW_SYMBOLIC=1` 56.7 s. So the
BLAS pin alone makes UMFPACK 1.31x faster than the Elmer build did, and PARDISO is a further 1.28x.

Accuracy against UMFPACK (where PARDISO converged): terminal currents <= 8.6e-16 relative (identical
to the last digit at 0 V and -0.4 V), Potential <= 1.1e-16 V absolute, electron and hole densities
<= 8.1e-15 relative. So PARDISO is as accurate and 1.3x (quiet box) to 2.0x (loaded box) faster on
these sizes.

The cause is DEVSIM's documented PARDISO behaviour (CHANGES 2.6.0): from the second Newton
iteration on it reuses the symbolic factorisation while the sparsity pattern is unchanged, "which can
result in numerical differences"; here (18k-node mesh) the Newton iteration stalled with the
continuity-equation RelError near 1e3 and gave up, and turning the reuse off (nothing else changed)
makes it converge. `DEVSIM_NEW_SYMBOLIC` (or `solve(...,
symbolic_iteration_limit=-1)`) turns the reuse off. In the validation run (`out_mkl`, pip-mkl venv,
pre-fix): `bipolar_diode_2d` FAIL (GATE A, 3/3 biases), `gated_dd_2d` and `carriers_3d_dd` PASS with
printed values identical to UMFPACK; with `DEVSIM_NEW_SYMBOLIC=1` `bipolar_diode_2d` PASSES with the
same printed currents.

What D0 does with this: the pin keeps devsim's own choice (MKL-PARDISO whenever pip mkl is
installed; not a default change) and, in that branch only, sets `DEVSIM_NEW_SYMBOLIC=1` unless the
user already set it (`test_mkl_pin_keeps_a_user_new_symbolic_setting`). With that, the 30 devsim
test files pass in the mkl venv (524 passed, 189 s, `-n 2`) as they do without it (524 passed). The default stays UMFPACK for everyone without mkl. MKL is not made a dependency.

Recommendation: keep it this way. PARDISO with a fresh symbolic factorisation is as accurate as
UMFPACK and faster, so `[pardiso]` users lose nothing. Making it the default would mean making
`mkl` a dependency (~700 MB, Intel-only optimisation), which is your call; nothing here requires it.
If you would rather have DEVSIM independent of whether mkl happens to be installed (CI parity), the
alternative is to rank scipy's OpenBLAS above MKL in the pin, which forces UMFPACK everywhere; that
is a one-line change but it is a behaviour change for `[pardiso]` users, so it is listed under open
questions rather than made.

## 5. Performance: `physics_equilibrium.setup_semiconductor_region`

Measured on 2.11.2, before any change: `tests/test_devsim_smoke.py::test_devsim_equilibrium_smoke`
152.3 s (pytest `--durations`; 310-358 s on 2.10 per the brief). Every devsim call of that test
wrapped with a timer (253 s total in that run, under load):

| call | time | count |
| --- | --- | --- |
| `node_model` | 252.9 s | 4 |
| of which `Electrons:Potential = simplify(diff(N_c * F_1/2(eta), Potential))` | 252.9 s | 1 |
| `solve` | 0.1 s | 3 |
| everything else | < 0.1 s | |

So 2.11.2 did not fix it; one symbolic call is the whole cost. `ds.symdiff` timings on the same
expression: `diff()` alone < 1 ms; `simplify()` of F_1/2 itself (no derivative) 71.7 s; the
derivative's `simplify(diff())` 150-273 s depending on load. The result contains only parameter
names (`N_c`, `Phi_c0`, `V_t`), never values, so it is the same string for every region and device.

Fix: `physics_equilibrium._SIMPLIFIED` maps the exact input string to DEVSIM 2.11.2's own output for
it (1154 characters, as returned by `node_model`), and `simplified(expr)` returns the stored result
on a hit and `expr` unchanged on a miss. Changing a fit coefficient or the eta string changes the
key, so a stale derivative is never reused; the code then falls back to DEVSIM's live simplify (slow
but correct).

Bit-identity evidence:

* Model level (4001-node 1-D region, eta = -40 .. 100, N_c = 2.8e25, Phi_c0 = -0.1234567): the
  replayed string and the live `simplify(diff())` give bit-identical `Electrons:Potential` on every
  node. Both agree with the unsimplified `diff()` to 9.3e-16 relative. (DEVSIM's re-print of the
  replayed string is not character-identical to the input, but the evaluated values are.)
* Solve level: `test_devsim_smoke`'s equilibrium bar AND drift-diffusion bar solved in one process with
  the live simplify (`_SIMPLIFIED` cleared) and with the replay: sha256 of all extracted grid fields
  `915301b5ae172ce0...` (equilibrium) and `afff991044ea849b...` (DD) in both, i.e. bit-identical;
  the live run took 317 s for the equilibrium solve (loaded box), the replay 0.3 s.
* Gates, `tests/test_equilibrium_simplify_cache.py`: the cache key is exactly what
  `setup_semiconductor_region` builds (devsim-free); the cached derivative matches DEVSIM's
  unsimplified `diff()` to <= 1e-13 relative over that sweep (fast); `@slow`: the live
  `simplify(diff())` prints the identical string and evaluates bit-identically (passed, 311 s).

Speedup: the equilibrium smoke solve goes from 152 s to 0.3 s (the `Electrons:Potential` model from
~150-270 s to 0.5 ms), i.e. the test is ~500x faster and every equilibrium semiconductor region
saves 2.5-4.5 min of setup.

Test-suite effect (pytest `-n 2`, loaded box): `tests/test_devsim_smoke.py` 314 s on the pre-D0
code (`test_devsim_equilibrium_smoke` alone 305 s) -> 21 s with D0 (that test no longer in the top 3;
slowest is 6.5 s). The 30 devsim-using test files run in 158 s in total.

Not done: DEVSIM's other `simplify(diff())` calls (eq_registry `node_with_derivs` / `edge_with_derivs`
for the drift-diffusion, bipolar and density-gradient models) are not on the slow path: the whole
drift-diffusion smoke (setup + solve) takes 2.7-3.4 s, and the bipolar 2-D diode spends 132 of its
138 s in `ds.solve` (section 4), so they are left live.

## Open questions (decisions that belong to the user)

1. Linux/macOS default BLAS. The pin is on by default on Windows only. On Linux devsim keeps its
   own loader search (CI: apt `libopenblas.so`; a box without it: reference `liblapack.so`, as in the
   WSL run above). `DYNAMETA_DEVSIM_BLAS=pin` gives Linux the same scipy-OpenBLAS pin (tested under
   WSL). Making that the Linux default would change which BLAS CI and Linux users get; not done.
2. `[pardiso]` users and DEVSIM. With pip mkl, DEVSIM uses MKL-PARDISO (its own choice, kept), now
   with `DEVSIM_NEW_SYMBOLIC=1`. If you would rather keep DEVSIM on UMFPACK whatever is installed
   (CI parity; PARDISO is 1.3-2x faster and as accurate here), rank scipy's OpenBLAS above MKL in
   `configure_math_libs()`. Not done: it changes `[pardiso]` users' solver.
3. MKL as a dependency: not added and not needed.
4. Commit headroom outside D0: `dynameta.carriers.electrostatics_fem` imports ngsolve at module
   import, and `ngsolve_openblas` commits ~4 GB per process at load (MAX_THREADS=128, ~32 MB per
   thread). That is most of the ~6 GB a fresh carriers-hygiene child holds, and it is what still ran
   the box out of commit at 24 concurrent copies after the pin. A lazy ngsolve import there, or an
   `OPENBLAS_NUM_THREADS` policy for test children, would fix it; both are outside D0.
5. The cached simplify string is DEVSIM 2.11.2's output. If a future devsim simplifies differently
   the `@slow` gate fails on the string comparison while the cache still holds a correct derivative
   (it matches the unsimplified `diff()` to 9.3e-16). Regenerate it then, or accept it as is.

## Release-note lines (for docs/audit/*release*.md)

* **DEVSIM floor `devsim>=2.11.2`** (`[solvers]`): `reset_devsim()` now keeps the UMFPACK solver
  (devsim #169), DEVSIM_BLAS_PREFIX/SUFFIX exist (#167).
* **DEVSIM's BLAS is pinned before the first import** (new `dynameta.carriers.devsim_env`, the one
  devsim import home). On Windows, with `DEVSIM_MATH_LIBS` unset, DEVSIM no longer takes whatever
  `libopenblas.dll` is first on PATH (on the dev box: a 2019 OpenBLAS 0.3.7 from an Elmer install,
  which crashed fresh-process imports under load, 9/72 at 24 concurrent copies -> 0/144 access
  violations after). Order: user `DEVSIM_MATH_LIBS` (always wins) > pip mkl's mkl_rt (full path) >
  scipy's bundled LP64 OpenBLAS (prefix `scipy_`) > devsim's own search. Linux/macOS unchanged by
  default; `DYNAMETA_DEVSIM_BLAS=pin|off|auto`.
* **pip mkl (`[pardiso]`) switches DEVSIM to MKL-PARDISO** (devsim's own behaviour, now documented).
  dynameta sets `DEVSIM_NEW_SYMBOLIC=1` in that case: with DEVSIM's default symbolic-factorisation
  reuse the 2-D bipolar diode validation did not converge at any bias. PARDISO then matches UMFPACK
  to <= 1e-14 and is 1.3-2x faster.
* **Equilibrium semiconductor regions set up ~500x faster**: the Fermi-integral Jacobian's DEVSIM
  `simplify()` (150-300 s per region) is replayed from a stored DEVSIM 2.11.2 result, bit-identical
  (`test_devsim_smoke.py` 314 s -> 21 s; the 33 devsim validations 8890 s -> 2740 s, e.g.
  `gated_dd_2d` 253 s -> 2.4 s, `carriers_3d_multisemi` 1285 s -> 19 s).
* `validation/ac_capacitance.py` clears state with `reset_devsim()` (bit-identical C/G).
* All 33 devsim validations and 30 devsim test files pass on 2.11.2 with no tolerance changed; devsim
  2.10 -> 2.11.2 moved no printed value (the only round-off-level movements come from the BLAS change).
