# v0.15 Linux CI: four exactness failures (2026-11-08)

PR #36's `solvers-devsim` job (ubuntu-latest, Python 3.12, OpenBLAS 0.3.26, glibc 2.39) failed four
tests that pass on the Windows dev box (Python 3.14, UCRT). All four were reproduced in the local WSL
proxy of the runner. None of them was a physics bug. Three gates asserted more than IEEE arithmetic
promises across platforms. The fourth had a sign error in its own round-off budget. One product change
came out of this: the stall rule in `dc_solve`. It only decides whether a failure message carries the
conditioning diagnosis; no solved value changes.

Every number below was MEASURED by me on both platforms with probe scripts, the same fixtures and the same
commit, unless it is marked as inferred.

## (a) `test_well_posedness.py::test_mos_inversion_stall_carries_the_near_singular_diagnosis`

**Symptom.** On CI the reported `sigma_min/sigma_max` was 1.4e-15, against the assertion `<= 1e-15`.
In WSL the test failed one step earlier, both alone and as part of the full file: the stall message carried
no diagnosis at all.

**Mechanism.** The test drives a 1-D MOS inversion layer to the double-precision floor. There, two things
are set by round-off.

1. *Where the stalled Newton ends.* Along the near-null mode, round-off in the update is amplified by
   1/sigma_min (u / 1.7e-17 is about 6). Windows stalls at 0.78 V and the relative update wanders between
   3e-10 and 4e-7 until the end. Linux converges at 0.78 V and stalls at 0.80 V. There the update reaches
   4.7e-5 at iteration 13, jumps to 1e3, and ends at 6.5e-2. The old rule in `dc_solve._stalled` looked
   only at the LAST iterate (stall = "last relative error < 1e-2"), so on Linux it decided this was not a
   stall and attached no diagnosis.
2. *The reported ratio.* The true equilibrated ratio is below double resolution. Two other algorithms give
   1.6e-17 / 1.9e-17 (`gesdd` without vectors, Windows / Linux) and 1.6e-17 / 3.7e-17 (inverse
   iteration on a sparse LU). The dense SVD with vectors, which the diagnosis uses, returns its own
   round-off: 4.4e-16 (exactly 2 eps) on Windows, 3.6e-15 (16 eps) in WSL, and 1.4e-15 on the CI runner,
   which had a different process history.

**Fix.**

- `dc_solve._stalled`: a failure is a stall when it used every iteration and the BEST iterate came within
  `_STALL_REL` = 1e-2. Measured best iterates: 2.7e-10 on Windows, 4.7e-5 on Linux.
- The jump refutation (0.76 V to 1.2 V) now runs 10 iterations, which stay at or above 1e3 on both
  platforms, so it is clearly far from a solution. Over 40 iterations its best was 1.9e-2 / 4.5e-2, only
  2-5x above the rule. That was a refutation sitting on a knife edge.
- Ratio budget, derived before measuring. LAPACK's SVD is backward stable: the computed singular values
  are the exact ones of J_eq + E, with ||E||_2 <= p(n) u ||J_eq||_2. The LAPACK Users' Guide (3rd ed.,
  section 4.9) calls p "a modestly growing function"; the gate takes it as linear, p(n) = 2n. Weyl's
  inequality then gives: reported ratio <= true ratio + n eps. For 804 unknowns that is 1.8e-13. This is
  5.6x below `NEAR_SINGULAR` (1e-12) and 130x below the 0.30 V ratio. The measured values use 0.002
  (Windows) and 0.02 (WSL) of the budget.

**The gate still bites.**

- `_sigma_ratio` returning s[-2] (an off-by-one: 6.0e-7) fails on both platforms.
- The old last-iterate rule fails on Linux (no diagnosis).
- Code without the diagnosis fails, as before.

**Latent sibling (not changed; outside this task).** `test_quasi_equilibrium.py::test_closure_removes_the_near_null_mode`
divides by the same kind of SVD-noise sigma_min (full 2.6e-16) in `closed / full >= 1e8`. If a platform's
SVD noise were about 10x larger it would fail. It passed on CI.

## (b) `test_devsim_oxide_tunneling_sc.py::test_o10_..._tunnel_shot_source[n_dep]`

**Symptom.** `one_sided == 0.0` failed on CI with 2q|J| = 5.41e-40.

**Mechanism.** At equilibrium, x_s (DEVSIM's activity of the solved n_s) and
x_g = (psi_s - phi_c - V_g)/V_t are the same Fermi level computed two ways. On Windows they round to the
same double, so J = 0 exactly. On Linux x_s is one ulp below x_g (-14.980390283369633 vs ...632). That
gives J = -1.69e-21 A/m^2, or 1.8e-15 of J_fwd, which matches the linear response dJ/dx_s (x_s - x_g) to
1 %. Nothing guarantees exact zero.

**Fix.** A bound from detailed balance. With a = x - eps/kT and N = kT softplus(a):

- |N(a_s) - N(a_g)| <= N |a_s - a_g|, because the logistic is never larger than the softplus.
- |a_s - a_g| <= |dx| + 2 eps A, with A = |x_s| + eps_max/kT (two roundings of x - eps/kT).
- Each N is evaluated to 4 eps.

So |J| <= max(J_fwd, J_bwd)(dx_max + 2 eps A) + 4 eps (J_fwd + J_bwd). Here dx_max =
re (1 + (|psi_s| + |phi_c| + |V_g|)/V_t) carries the DC solve's relative tolerance (re = 1e-12) over to x:
6.8e-11 for n_dep, 8.5e-11 for n_acc. The gate asserts |x_s - x_g| <= dx_max, the bound on |J|, and
one-sided / (4kT G) <= bound <= 1e-10. That bound is 3.4e-11 (n_dep) and 7.2e-11 (n_acc), so the
refutation still reads "the one-sided formula misses by -100 %". Measured: |dx| <= 1.8e-15, and |J| uses
at most 2.6e-5 of the bound. The child now also reports x_g, the potentials divided by V_t, and the top of
the energy grid.

**The gate still bites (kernel evaluated at the n_dep state).** A 1e-9 Fermi split at "equilibrium" gives
|J|/J_fwd = 1.0e-9, which is 15x the bound's 6.8e-11. A 10 % heavier supply mass on the gate side breaks
detailed balance and gives 0.10.

## (c) `test_devsim_noise_thermionic.py::test_t0_3d_area_is_devsims_assembled_area[jitter_exact]`

**Symptom.** The assertion message printed the largest difference, 1.58e-30 (r_hi), which looked like a
budget miss. That was misleading: the node that actually failed had a difference of exactly 0.

**Mechanism.** A bug in the test's round-off budget, 16 eps (P_row + |w|).

- P_row was written as |ElectronCurrent| x EdgeCouple.
- `devsim_geometry.apply_exact_geometry` writes the SIGNED exact EdgeCouple. It is negative on 1106 of
  r_lo's and 236 of r_hi's edges on the jittered stack; DEVSIM's own couples are unsigned.
- At an equilibrium node whose currents are round-off, that "magnitude" therefore summed to a negative
  number. On Linux, r_lo node 64 had P = -3.0e-24 with w = code = 0. A negative budget fails even an exact
  match. On Windows the round-off happened to give P = +4.4e-24 at the same node.

**Fix.** Use the magnitude of every product: |ElectronCurrent x EdgeCouple| and |ElectronGeneration x
NodeVolume|. After the fix, max |w - code| / budget is 0.093-0.146 on both platforms.

**The gate still bites.** The geometric split (interface_node_area) misses by 1.6e14-3.6e14 times the
budget on the jittered meshes.

## (d) `test_fd_mode_complete.py::test_d_legacy_statistics_definition_is_byte_identical`

**Symptom.** On Linux the 501-call log hashed to 71a3219d... instead of the recorded dcca0b09....

**Mechanism.** I dumped and diffed both logs. They differ in one numeric literal: 6206809661957.206 on
Windows vs ...205 on Linux. It occurs 12 times in 9 calls, all in the interface-trap charge and
recombination strings (ItCharge0, ItRecomb0 and their derivatives). With the numbers masked, the text is
identical. The literal is n1 = n_i exp(-7.384693350077327) for D_it bin 14. Its inputs (E, kT, the
quotient) are bitwise equal on both platforms. Checked against mpmath at 200 bits:

- the Windows UCRT `exp` is 0.510 ulp from the exact value: wrongly rounded, a hard case;
- glibc is 0.490 ulp from it: correctly rounded.

Glibc rounds all 88 of the fixture's level exponentials correctly; UCRT misses this one. The digest
therefore pinned a last bit that IEEE-754 leaves to the C library. That is a fragile construction, not a
code change.

**Fix: a canonical form.**

- New `tests/_cr_libm.py`, a context manager `correctly_rounded()`. While it is active, the
  transcendental entry points of `math` and numpy (exp, expm1, log, log2, log10, log1p, pow / power)
  return the correctly rounded double. They are computed with stdlib `decimal` at 60 digits (199 bits).
  decimal's exp and ln are correctly rounded at the context precision, and the hardest binary64 cases of
  exp and log need fewer than 160 bits (Lefevre & Muller 2001). So the double is correctly rounded for
  every argument. Checked against mpmath at 300 bits on 6004 arguments, including this one: 0 mismatches.
  The Windows platform `np.exp` misses 45 of the same 6004.
- Every other transcendental refuses inside the context. A recorded path that starts calling one gets an
  error instead of a silently platform-dependent digest.
- `record_call_log(canonical=True)` is now the default. The digest was re-recorded on an export of
  2fb4b76, the commit the original was recorded on: 71a3219d... on Windows and on Linux, the same as this
  tree on both. On Windows the raw (platform libm) log of 2fb4b76 still gives dcca0b09..., which confirms
  that the reference is the same code. In this fixture, glibc's raw log is already the canonical one.
- The log keeps every IEEE operation bit for bit. That is why this is a canonical form rather than a
  tolerance: a tolerance on the literals would have to allow the 32 ulps by which the cancellation in
  SeedPsiShift amplifies a 1-ulp libm difference (measured by nudging every libm result by one ulp), and
  would then miss real ulp-level changes.

**The gate still bites (canonical form, measured on both platforms).**

- n1 = n_i (3 exp(e)) / 3 instead of n_i exp(e): one extra rounding, mathematically the same value. It
  moves 370 literals by 1-2 ulps, leaves the text with numbers masked unchanged, and changes the digest.
- The FD reference densities in the legacy SRH string (srh_reference_densities with fd=True) change it.
- The v0.15.0 default (FD statistics) still differs from legacy, as asserted. It is now checked on the
  text with numbers masked, which is stronger than a digest inequality.

**Cost.** The correctly rounded functions go through `decimal` one element at a time (about 35 us each).
The legacy log takes 24 s to record instead of 15 s. The FD-statistics path evaluates about 2e6
`np.power` elements (its FD tables) and would take 466 s. The default-vs-explicit-FD comparison is two
logs from the same process, so it is platform-stable as raw logs; it stays raw. Gate D measured 44 s on
Windows and 20 s in WSL. It was 16 minutes when everything was recorded canonically.

**Not covered.** The C `pow()` behind the `**` operator cannot be intercepted. A trace of every line
executed while the log is recorded shows the fixture reaches it at:

- import-time constants: tunneling.py `100.0 ** -P` and `E_J ** 1.5`, constants.py `C ** 2`,
  bipolar_options.py `x ** (1/3)`;
- fd_potential_shift: `s ** 3` on arrays.

All of these are bitwise equal on UCRT and glibc: the raw logs differ only in the exp literal.

**Same construction elsewhere (latent; not changed).** `tests/_bipolar_calllog.py`, `_btbt_calllog.py` and
`_dg_calllog.py` hash raw logs in the same way. They pass on Linux today only because none of their
literals hits a hard-rounding case. Recording them under `_cr_libm.correctly_rounded()` (and
re-recording their digests on their reference commits) would remove that exposure.

## Release-note lines

- A stalled `solve_dc` Newton now gets its near-singular diagnosis whenever any iterate came within 1e-2
  of a solution. Before, only the last iterate counted, and that one is chance at the double-precision
  floor. No solved value changes.
- Test infrastructure: the call-log gates can record a canonical log (correctly rounded transcendentals,
  `tests/_cr_libm.py`), so a recorded digest no longer depends on the platform's C library.
